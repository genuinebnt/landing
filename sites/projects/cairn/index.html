ENGINEERING DEPTH

Four algorithms carry this project. Each one is drawn on screen as it runs, which is only possible because span emission was built into layer 1 rather than retrofitted after.

JOIN-ORDER DP

Exhaustive DP over relation subsets with a real cost model from catalog statistics — then a GEQO-style genetic fallback once N makes the table stop fitting. The cliff is shown, not hidden.

B+TREE & LATCH CRABBING

A reader releases the parent latch the moment the child is latched, so descents overlap instead of serialising. The hardest part of a B+Tree to get right, stepped one frame at a time.

RAFT & THE WAIT-FOR GRAPH

Hand-rolled Raft for coordinator HA and catalog replication, plus a lock wait-for graph with cycle detection — a deadlock is a cycle you can literally watch close.

ARIES RECOVERY

Write-ahead logging with the three ARIES passes, and a crash you can inject yourself at any point on the timeline to watch analysis, redo and undo do their work.

BUFFER POOL

LRU-K, ARC and Clock run against the same access trace side by side, so the difference between replacement policies is visible rather than asserted.

EXCHANGE & SHUFFLE

The shuffle boundary is where a distributed engine stops resembling a single-node one, so exchange gets first-class treatment in the trace — including backpressure in both directions.

The single public entry. Accepts a statement, opens a trace, and streams span events back to the browser while the query is still running — so the UI renders progress rather than a final result blob.

Lexer, recursive-descent parser, logical plan, then the physical plan and its fragment placement. The DP table is emitted as trace data, which is what makes the optimiser view exact rather than illustrative.

Where the database-internals work lives: heap and columnar page layout, a buffer pool with a real replacement policy, B+Tree indexes, the lock manager, and a Volcano iterator that later goes vectorised.

catalog

Its own gRPC service backed by Cloud SQL. Bad statistics are the usual reason a plan is bad, so the UI shows estimate against actual side by side for every operator.

metadata (raft)
owns: cluster state, leases, shard ownership
Raftconsistent hashing2PC coordinator

The only strongly-consistent store in the system. Everything else may be stale; membership and shard ownership may not. Elections and log replication are drawn live in the distributed view.

specialised workers

Vector and graph workers federated behind the coordinator through the same table interface, so one query can span row, column, vector and graph storage without the planner special-casing any of them.

THE SEVEN LAYERS

Two motions, not one sequence. Every layer gets a thin working MVP first; once all seven exist they wire into a walking skeleton on GCP, and only then does each layer get its own expansion track — picked in any order, re-integrated as it lands. There is no stage six where depth finally happens.

DECISIONS WORTH DISCUSSING
sequencing

MVP every layer thin, then combine, then deepen — rather than finishing layer 1 before starting layer 2. A linear sequence would mean the distributed and cloud work never gets touched until the single-node engine is “done”, which is to say never. The seams get proven while they are still cheap to move.

tracing

Span emission was built in layer 1, not retrofitted. Every later layer inherits the visualisation for free instead of needing a bespoke debug view, and the trace contract in ARCHITECTURE.md is what Cloud Trace later plugs into unchanged.

optimiser

Exhaustive join-order DP is O(3ⁿ) and stops being viable around a dozen relations. Rather than hide the cliff, the optimiser lab lets you raise N until the DP table visibly stops fitting and the genetic fallback takes over. The failure mode is the lesson.

consensus

Raft holds cluster metadata only, never query data. Putting shard ownership behind consensus and leaving everything else eventually consistent keeps the quorum path off the hot path — a query never waits on an election unless membership actually changed.

non-goals

No Postgres wire-protocol compatibility, no WASM, no multi-tenant SaaS framing. Cairn speaks its own SQL surface over its own API, and nothing runs client-side — the whole point is real server processes with real network hops between them.

design

Colour encodes engine state and nothing else — amber is running, teal is a hit or a commit, red is a real failure, violet is blocked on a lock or a quorum. A reader who learns that amber also means “the storage layer” has learned that amber means nothing.
